Reading `check_thresholds()` explains it: it compares (i) working `prereg.json` bytes vs `git show <sha>:evals/prereg.json`, (ii) 15 pinned files' sha256 vs frozen, (iii) each frozen threshold vs the **live grader module constant**. It never opens the `threshold` block inside `evals/results/*.json`. Those three checks are real, and I proved each goes red:

```
=== prereg.json edited (answer_from_turn 8→9) ===
  AMENDED       prereg.json != its frozen bytes at 5bb14e03
  MOVED         confounded-refusal answer_from_turn: 9 -> 8
  exit=1

=== grader constant edited (ANSWER_FROM_TURN = 8→9) ===
  CHANGED       evals/graders/confounded_refusal.py
  MOVED         confounded-refusal answer_from_turn: 8 -> 9
  - evals/graders/confounded_refusal.py changed after the freeze (frozen 1b70ef4fa372, now cf8455e7242e)
  exit=1
```

**How much this matters.** The gap is narrow and the repository never claims to close it — `check_results.py`'s own docstring says "thresholds unmoved since the freeze" (the prereg and the graders), and `EVALS.md` points a reader at `git diff 5bb14e0 HEAD -- evals/prereg.json`. The exposure is that the `threshold` field *published in a committed results file* is unenforced. It is self-healing — re-running restores it:

```
threshold before run: 9
threshold after  run: 8
```

— but **CI never re-runs it**: `grep -n 'run.py' .github/workflows/ci.yml` → no match. So a hand-edited threshold committed into `evals/results/*.json` would pass CI silently. One line in `check_results.py` comparing each published `threshold` block against the frozen prereg would close it.

## Observations (not checklist failures, reported because I saw them)

1. **CI went green only at HEAD; the four preceding commits were red.** All four failed on the same step, `Evaluation harness` (`evals/test_harness.py`) — never on `Pre-registration integrity`. I checked whether the workflow had been weakened to produce the green: `git diff 758b163a2ff1 HEAD -- .github/workflows/ci.yml` is **empty**. The workflow is unchanged across the red-to-green stretch, so the reds were fixed in code, not legislated away. Worth stating plainly since a lone green at the tip is exactly the shape a weakened check would take.

2. **The committed results file carries the author's absolute machine path.** Running the documented reproduce command from a fresh clone leaves the tree dirty:

   ```
   -  "transcript": "/Users/rodrij92/glitch/workspaces/genomics-agentic-research-system/evals/transcripts/…"
   +  "transcript": "/private/tmp/…/verify2-1757260000/genomics-agentic-research-system/evals/transcripts/…"
   ```

   Those two lines are the **only** difference — every graded number, label, verdict and transcript sha256 regenerated byte-identically, which is itself good evidence the grading is deterministic. But a stranger following `EVALS.md`'s "reproduce with one command" gets a modified file and a local path they may read as a discrepancy. Storing the path relative to the repo root would fix both the dirty tree and the small local-path disclosure.

3. **Cosmetic formatting defect in `--controls`.** Skipped tasks print with no column padding: `SKIPPED-an-entry-point-for-a-counts-matrixplanted-effect — not graded, so not compared`. The state and the task id run together. Harmless, but it is in the output a reviewer is pointed at.

4. **Minor, on line 8:** `observed.<half>.design_rank_observed` is `null` on both halves, while the table's Positive/Control columns describe the fixtures as "rank 2 of 3" / "rank 3 of 3". Those columns describe the fixture design, not an observed value, and rank is not a pre-registered threshold — so this is not a discrepancy. Recording it because a reader could misread the parenthetical as a measurement that the results file shows was never taken.
