### MAJOR

#### M-1 — Row 4 (and 15, D-1): the guard does not cover the development surface, and the assessment never says so

**Claim under review.** Row 4 treats `guard_hook.py` and `gars/.claude/settings.json` as the policy layer and scopes its bypasses to what that hook lets through. The security summary calls these "live weaknesses in the code that ships today".

**What I found.** The hook is wired only for a session whose project root is `gars/`.
- The repository root has no `.claude/` directory, no `AGENTS.md`, and no other hook configuration.
- The root `CLAUDE.md` directs development work (where v1.0.1's builds happen) to run from the repo root.
- In such a session no guard runs at all: every protected path in R-094 (`_system/`, `.claude/settings.json`, CI config, `docs/decisions/*`) is writable by any means, not only via the interpreter bypasses the assessment lists.
- Even inside `gars/`, the hook sees only paths under `gars/`: Write to `../.github/workflows/ci.yml` or `../docs/decisions/…` is outside its root and allowed.
- The spec names Codex as the builder (R-162) and R-161 requires the gates "under one harness's hook format". The repository carries hook configuration for exactly one harness, at one directory level.

**Evidence.**
- `ls -a <clone>` shows no `.claude`; `ls -a gars/.claude` → `settings.json` only.
- `guard_hook.py:65-67` sets the root from `CLAUDE_PROJECT_DIR`, and `:76-77` returns `None` (allow) for paths outside it.
- Probes: Write `../.github/workflows/ci.yml` → exit 0; Write `../docs/decisions/0022-x.md` → exit 0; Write `.githooks/pre-commit` → exit 0.
- The root `CLAUDE.md` "Before committing" section is development-mode guidance with no hook.

**Recommended correction.**
- Add a row 4 sub-item "guard scope": wired only for `gars/`-rooted Claude Code sessions; the repo-root development session and any non-Claude builder are unguarded.
- Extend D-1 so the owner decides with that scope in view.
- Row 15's "project-local hooks" dependency should note that git-level hooks are the only mechanism that would cover the repo-root session and a Codex builder alike.

#### M-2 — Row 4 (R-073): forgery does not need a hand-written line; `approve` is agent-invocable and records no actor, and `verify` re-checks nothing

**Claim under review.** The summary and row 4 state that "a hand-written `Status: APPROVED` line passes stage 03 `verify`".

**What I found.** That reproduces, but it understates the defect in two ways.
1. **The legitimate `approve` subcommand can be run by the agent with no human involved.**
   - `stage03_analysis.py approve` checks only the plan's shape (`:199-243`) and stamps `Status: APPROVED <date>` (`:246-248`).
   - The guard allows `python3 _system/stage03_analysis.py approve …` (exit 0), like any `_system/` script.
   - No actor is recorded. R-073 requires "the actor is a launch-time fact, not a CLI flag".
2. **`verify` re-validates nothing `approve` enforces.**
   - `cmd_verify` (`:255-316`) checks only the regex at `:265` and that the declared outputs exist and are non-empty.
   - A plan that `approve` would refuse still passes: out-of-vocabulary artifact type, invalid `Runs:` venue, or no `Status: DRAFT` history. `verify` then writes `OUTPUTS.tsv` rows with the unvetted type and `STATUS COMPLETE`.
   - So the closed artifact vocabulary and the venue gate (decisions 0027/0039) are bypassable by the same single edit.

**Evidence.**
- Probe A: a DRAFT plan filled with a valid type, then `stage03_analysis.py approve --project … --analysis 02_agent-approves` run by a script → exit 0, `"status": "Status: APPROVED 2026-09-13"`.
- Probe A, guard: the same `approve` command line as Bash → exit 0.
- Probe B: hand-written plan with type `not_a_vocabulary_type` and `Runs: whatever` → verify exit 0, `STATUS: COMPLETE …`.
- The committed Gap Study control records the first point independently: `evals/gap-study/prereg.json`, task `plan-gate`, layer evidence "approve returned ok and stamped the plan APPROVED with no person having answered anything".

**Recommended correction.**
- Rewrite the row 4 approval sub-item and the security summary as: "approval is forgeable two ways, by running `approve` (no human, no actor) or by writing the line; `verify` trusts the plan's content without re-running `approve`'s checks".
- Add `verify`-side re-validation to the "Change, each with an R-042 record" list.
- Note that the Gap Study already holds this as committed evidence.

**Evidence.**

- Scope: this path fires only through `prepare` then `submit`, which on this machine skip for lack of a pinned checkout. The construction was reproduced from the wrapper's own format strings, not by a full `prepare`.

**Recommended correction.**
