# The executor is a workspace setting, not a spelling

## What happened

GARS was written on one cluster, and that cluster's scheduler leaked out of the assumption
layer into the artifacts. `wrapperlib.write_submit_sh` wrote `#SBATCH` directives into every
generated `submit.sh`; `write_reproducibility` recorded `sbatch <path>` as the literal
submission in `commands.sh`; stage 03's venue vocabulary was the two strings `sbatch` and
`login-node (user-requested)`; and six sub-stage contracts instructed the agent to run
`sbatch` and poll `sacct`/`squeue` by name.

None of that was wrong on the cluster. It meant, though, that GARS could not run anywhere
else — not on another lab's PBS or LSF or SGE, not on cloud batch, and not on a laptop for
the deterministic tests, which had to exercise `prepare` and stop short of the submit → status
→ collect walk the whole system is built around.

The trigger was a second venue becoming real: the same pipelines needed to run off-HPC. The
choice was to fork the submission path or to open a seam. A fork would have meant two sets of
generated bytes to keep in step, and the one property that matters most on the cluster — that
an upgrade changes nothing — would have depended on nobody making a mistake in the copy.

## Decision

**One door, chosen by configuration.** `_config/executor.yaml` describes the workspace's
scheduler, and `_system/executorlib.py` answers three questions from it:

- `header` — the directives block a generated `submit.sh` opens with;
- `submit <script>` — the argv that hands **that generated script** to the scheduler,
  returning a job id;
- `status <job_id>` — the argv that asks after it, mapped onto a closed four-state vocabulary,
  `PENDING | RUNNING | COMPLETED | FAILED`.

The descriptor is seeded by stage 00 alongside `nextflow.slurm.config` and it is
**optional by deletion**: with no file, or with `name: slurm`, the built-in Slurm descriptor
applies and the generated bytes are identical to what this system produced before the seam
existed. That is not a claim, it is a test — `tests/run_tests.py` compares against fixtures
captured from the pre-seam code, for a strict-parser assay and a legacy-parser one. A cluster
that pulls this change notices nothing.

`submit_argv` runs the generated script and nothing else. It is not a second parameter
surface; the audited one is `_config/<assay>.yaml`, and the standing rule that pipeline
parameters go through it rather than around it — the same rule that makes the wrapper reject a
`params` block in the Nextflow config — applies to the descriptor unchanged.

A second built-in backend, `local`, runs the generated script detached and reports its PID as
the job id. It exists so the deterministic core can walk submit → status → completion with no
cluster at all — the half of the state machine the test suite could never reach. It is **not**
a venue for analyses: stage 03's gate is untouched, and nothing selects `local` by inference.

**Stage 03's venue vocabulary is respelled, not weakened.** `EXECUTION_VENUES` becomes
`("batch", "sbatch", "login-node (user-requested)")`. `batch` means the workspace's configured
executor; `sbatch` is accepted as its Slurm-era spelling, because every plan already approved
on the cluster carries that word and a decision record must not invalidate the record.
[0027](0027-stage-03-runs-under-sbatch-by-default.md)'s actual ruling — *the agent never
decides to run work in the current process; the managed executor is the default* — is
scheduler-agnostic and stands in full force. Only its spelling was Slurm-coupled.

## Why config, not code

The lineage is [0019](0019-config-is-seeded-not-authored.md) and
[0020](0020-config-decisions-come-from-menus.md): a setting the site owns is seeded for it and
chosen from what the system already knows, never typed into a helper as a branch. Where a site
differs from another site, the difference belongs in a file the site owns. A site that
needs PBS writes a descriptor; it does not patch `wrapperlib`, and it does not carry a fork.
`_references/genomes.md` already says the same thing about reference paths — "a different site
edits this file; nothing else needs to change" — and this is that sentence applied to the
scheduler.

## What this costs

The generated `submit.sh` now depends on a config file to know its own header. The mitigation
is that the default is built into the code rather than the file: deleting the descriptor is a
supported state, not a broken one, so the failure mode of a missing config is *the old
behaviour*, which is the safest thing a missing config can do.

A descriptor with a typo could in principle produce a script the scheduler rejects. So the
descriptor is validated as a precondition — every placeholder a directives line names, the
presence of `{script}` in `submit_argv` and `{job_id}` in `status_argv`, and every state in
`status_map` landing inside the closed vocabulary — and preflight reports each problem by
name, in the same `executor_config` failure class that already guarded the Nextflow config.
An unmapped scheduler state is refused rather than guessed at: reading an unfamiliar state as
success is the one failure this seam must never permit.
