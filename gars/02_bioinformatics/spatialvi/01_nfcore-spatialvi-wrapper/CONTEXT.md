# Sub-stage 02.01 (spatialvi): nf-core/spatialvi Wrapper

## Purpose
Run downstream spatial transcriptomics analysis — Space Ranger output to filtered, clustered,
spatially annotated AnnData objects — through `nfcore-spatialvi-wrapper` (decisions 0028, 0039).
This sub-stage submits the job and returns; it does not wait for completion. A later invocation
reads `STATUS` and collects results.

**The computation is not yours.** The wrapper's `check` validates, `prepare` writes
`params.yaml` and `submit.sh`, and `collect` runs the exit gate and writes `OUTPUTS.tsv` and
`STATUS`. Your job is the dialogue between those calls and the verbatim reporting of what they
return. `submit.sh` is generated by code — never write or edit it yourself.

## Inputs
1. **`01_samplesheets/spatialvi_samplesheet.csv`** — written by stage 01; two columns,
   `sample` and `spaceranger_dir`
2. **`_config/spatialvi.yaml`** — the QC thresholds, bin size and clustering resolution
3. **The wrapper** — `$GARS_WRAPPERS/nfcore-spatialvi-wrapper/nfcore_spatialvi_wrapper.py`,
   versioned in this workspace (decision 0012)
4. Reference (every run): `_references/artifact_types.md`, `_system/gars-env.sh`

## Scope Boundaries
This sub-stage performs the steps in Process and nothing else.

- Never compose a `nextflow` command, and never write or edit `submit.sh` or `params.yaml` —
  `prepare` generates both, and the audited parameter surface is `_config/spatialvi.yaml`.
- **Never run Space Ranger, and never offer to.** This assay consumes a Space Ranger output
  tree that already exists. Running it needs 10x's proprietary binary and a licence acceptance,
  and is deliberately unsupported. If the user has only raw FASTQs and images, say plainly that
  GARS cannot process them and stop.
- **Never adjust a QC threshold to make a sample pass.** `qc.min_counts` and its siblings decide
  which spots are real tissue; lowering one until a poor sample survives is manufacturing a
  result. A sample that filters down to nothing is a finding to report, not a parameter to tune.
- Never change `hd_bin_size` to alter cluster counts. It describes how the data was captured,
  not how you would like it analysed.
- Never edit the wrapper's code. If it errors, report the error verbatim and stop.
- Never substitute a hand-written analysis. If the wrapper cannot run, do not call Scanpy or
  Squidpy by hand and do not "approximate" the result. Report and stop.
- Never open, filter or re-cluster the produced `.h5ad`.
- Never modify the samplesheet, the design table, `00_data/`, or anything under
  `01_samplesheets/`.
- Never run the pipeline in the foreground, and never poll for it in a loop.
- Never resubmit a job whose STATUS is `SUBMITTED` or `RUNNING`.
- Never delete or move a populated `run/` directory; `check` refuses it for a reason.
- Do not interpret the biology. Report spot and cluster counts, paths and report locations only.
- If you believe a step should deviate, stop and ask. Do not act first and report afterwards.

## Definitions

**Wrapper invocation.** From the workspace root, on stock python:

```bash
python3 _system/wrappers/nfcore-spatialvi-wrapper/nfcore_spatialvi_wrapper.py <subcommand> \
    --project projects/<title>
```

Exit codes are the stage-helper standard: 0 ok, 1 failure (the JSON lists every failure),
2 refused (a gate), 3 usage. Branch on them; never re-interpret a failure as something to fix
silently.

**Failure vocabulary.** `preconditions` (an input file is missing), `config` (a key is absent or
invalid — a bin size outside 2|8|16, a non-numeric threshold), `config_unfilled` (`<REQUIRED>`
markers remain), `samplesheet` (header, a blank or missing `spaceranger_dir`, a repeated sample,
or a directory with no `outs/`), `pipeline` (the pinned **commit** is missing or wrong),
`executor_config`, `output_dir`. `collect` reuses the artifact type names — `h5ad`, `report`,
`qc_multiqc` — as its check names.

**The input is a directory, not FASTQs.** This is the first assay whose unit of input is a
Space Ranger output tree per sample, so its `00_data/spatialvi/files.csv` carries
`sample_id, spaceranger_dir` rather than the FASTQ columns (`workspace.INPUT_KINDS`). There are
no lanes here: a repeated sample id is an error, unlike scrnaseq where lanes repeat one.

**The pin is a commit, not a release.** nf-core/spatialvi has no current release. Its only tag,
`v0.1.0`, is dated 2023-03-31 and `git describe` places it 1,014 commits behind `dev` — it
predates Visium HD support. GARS pins commit `ccdfb48` and verifies it with `git rev-parse`.
Say this plainly if the user asks what version they are running: it is a development snapshot,
deliberately and knowingly, and the `HISTORY.md` entry records it as such.

**Execution venue.** The pipeline always runs under `sbatch` (decision 0027). Downstream-only
analysis is far lighter than an alignment pipeline — no index is built and no FASTQs are read.

**Produced artifacts.** `h5ad`, `report`, `qc_multiqc` — see `_references/artifact_types.md`.
`h5ad` and `report` are **directory-valued**: spatial writes them per sample, under
`<sample>/data/` and `<sample>/reports/`, so the set is the artifact and a consumer globs inside
it. `collect` also returns the exact per-sample paths, so nobody has to guess the pattern.

The exit gate checks **content**: every sample must have its own **processed**
`<sample>.h5ad` and its own report. `<sample>-raw.h5ad` sits beside the processed file and is
the pre-analysis object; it is **never** accepted in its place, and the refusal says so when it
is the only one present. That rule exists because the scrnaseq wrapper shipped the equivalent
defect — a glob that silently published a raw matrix when the processed one was missing.

## Process
1. Reply T1.
2. Read the STATUS file. If it is `SUBMITTED`, `RUNNING`, or `COMPLETE`, stop — stage 02's
   router already handles those states and should not have routed here.
3. Run the wrapper's `check`. Exit 1 → reply T5 with its `failures` verbatim and stop. Do not
   fix causes yourself: `samplesheet` usually means the source pointed at the wrong level of
   the Space Ranger tree, which is stage 00's business to re-link.
4. Run `prepare`. Exit 1 → reply T5 (same rule). Exit 0 → report nothing yet.
5. Submit with `sbatch <sub-stage dir>/submit.sh`. Capture the job ID.
6. Write `STATUS` as `SUBMITTED <job_id> <iso8601>`. Reply T2 and stop. Do not wait or poll.
7. **On a later invocation** where STATUS is `SUBMITTED` or `RUNNING`: query `sacct`/`squeue`.
   If still active, update STATUS to `RUNNING <job_id> <iso8601>`, reply T3, stop.
8. If the job has finished, run `collect` with `--model "<the exact model id you are running
   as>"` (decision 0024). Exit 2 → the run did not actually complete: write `STATUS` as
   `FAILED <iso8601>`, reply T4 with the wrapper's error and the Slurm log path, stop.
   Exit 1 → the exit gate failed: write `FAILED`, reply T4 with its `failures` verbatim, stop.
9. Exit 0 → `collect` has written `OUTPUTS.tsv` and `STATUS COMPLETE`. Append its
   `history_entry` to the project's `HISTORY.md` **verbatim**, replacing `<ISO-8601 date>`
   with today's date, and reply T6.

## Human check
Open each `run/results/<sample>/reports/report-<sample>.html` and read the **number of spots
retained after filtering** against the number the capture area started with, and look at the
clusters plotted **on the tissue image**. Confirm the retained spots still cover the tissue
rather than a corner of it — filtering that silently removes one region produces clusters that
look clean and describe an artefact, and nothing downstream will flag it.
