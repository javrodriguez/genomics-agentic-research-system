### Why the take image IDs changed

For take-a, take-o and take-g, the provisional and candidate images have equal Config, Created, RootFS layers, Architecture, Os, Size and full history.

- `Metadata.LastTagTime`

So the content is identical and only the index around it changed.
My inference, not yet checked by opening the index: BuildKit adds a per-build attestation manifest (provenance) to the index, so every build makes a new index digest even when every layer is cached.

The consequence for locks: an `image_id` pin names one build, not the content.
A reviewed pin should either record the config or manifest digest as well, or be built with provenance off so the ID can be reproduced.
