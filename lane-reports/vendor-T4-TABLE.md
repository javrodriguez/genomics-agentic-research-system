What PENDING does, per road (review 52b1f37 finding 3): on the take road a PENDING row is a refusal under the reason id named in its row with "no vendor reader yet", and after the agent's first turn every operator reason routes harness-error (routing.json driver_decided_reasons' source text: the generic operator-reason rows), so the take is refused, harness-error; it routes exactly as a Claude Code take with the same reason, so a higher-precedence row still wins for every arm alike (rate-limit routes pause; cgroup-kill routes aborted, except at cbf3c231 when the reasons include harness-condition-violated, T-18's PENDING reason).
On the walk road a PENDING row is recorded in check.json like any reason; the walk is graded, and it counts as coverage only as a Claude Code walk with that reason does (pending_walk.checker_standing, D/pending_walk.py:150-208: never counted when the reason is in CONSTANT_BOUND_REASONS, D/check_take.py:2452-2453); the freeze (plan section 7, leg ii) keeps any arm with an unsettled PENDING row out of a frozen order either way.
Because readers-disagree is in CONSTANT_BOUND_REASONS, arm G's PENDING run-tree row (T-4) means no gemini walk counts as coverage until T-4 is settled; the walk plan should expect that (review 10ac86f NIT 5). The same holds for any PENDING row whose reason id is in that list (unknown-harness-origin T-5 for O, constant-binding T-16 for O, environment-record T-17's billing-route leg, checkout-binding T-13 and T-14), so until those rows settle no walk of either vendor arm counts as coverage.
A pending vendor walk counts only through a verified checker reading under the merged constants in force (R-9, plan section 6, built in P5); a graded-true regrade alone never counts it.
Every PENDING cell is one key of check_take.VENDOR_PENDING_ROWS (the row, with a leg suffix where a row holds several: T-4 (G), T-5 (O), T-8:file-change (O), T-10, T-11 (G), T-12:offered-context (the session-side record of extra directories and tool servers), T-12:instruction-files, T-12:prompt-snapshot, T-12:memory, T-13, T-14, T-16 (O), T-17:billing-route, T-18), raised only through check_take.vendor_pending, and VP-keys binds the helper's call keys to the map's keys per harness (plan section 7).

- Account-email (row 9), the strings and the unit (review 10ac86f MINOR 2): C's check reads the presence of one field (session_context.userEmail, whatever its value) and counts 0 or 1 per take (D/check_take.py:697-716, 1910-1915). The vendor sweep counts, per harness, the operator's address and that harness's own vendor account address (codex: the ChatGPT account the leased auth.json signs in with; gemini: the Google account that owns the r4-g key), handed to the scan as ("email", value) secrets read by name at scan time, never written down; a harness with no recorded address refuses before launch. Any field of any record of any published vendor file that carries one of those strings is masked by the scan and makes the take's count 1, never more, so the unit is C's; the drive's bound (the checker's count not above the scan's masked email hits, D/drive.py:2886-2891) stays. The count is an event exactly as C's is, so no PENDING refusal is written under the account-email id, and the sweep stays even after a recorded walk shows no identity field.

- The host turn envelopes (plan section 6, edit B; glitch-b5 rounds 14 and 15): the drive writes each codex and gemini take's transcript.jsonl (one harness-turn envelope per ledger turn row, its sent the row's, its stream bound by basename and sha256, the CLI's own session id from that stream), which rows 2, 3 and 20's envelope legs, C3 and bound_items read; the ledger's transcript stays None for a vendor take. Without it no vendor reader runs on a real take (review e-71a2b94 finding 1). Edit C (round 15 ruling 2): right after the drive's scan, each envelope's sha256 and each ledger-named snapshot's sha256 in the driver ledger's native_snapshots are moved from the scan's sha256_before to its sha256_after, so the vendor readers bind the masked bytes they read. Named difference from arm C (round 16, review f-981e871 finding 1): a masked vendor file's pre-scan sha256 is not kept, where arm C keeps its transcript's in scrub.json; every count and reading is re-derived over the published bytes, so none depends on it; keeping it would need a frozen-reader change (a TAKE_FILE_KINDS line or a LEDGER_KEYS key), and box/scan_record's docstring warns that a pre-scan whole-file digest of a secret-bearing file can test a guessed low-entropy value offline.
