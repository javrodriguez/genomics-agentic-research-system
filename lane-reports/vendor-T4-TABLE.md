# T4 comparability table (cited by lane-reports/vendor-T4-PLAN.md v3, section 3)

One row per check the round-3 check() body and the round-4 checks raise; C = Claude Code, the reference.
Code is cited at harness head fb830f31 (branch codex/gap4-live-harness-20261013); `D/` is evals/gap-study-4/.
Classes: SAME (the vendor check reads CLI-written bytes for the same fact, at least as strictly); PENDING (held until recorded bytes settle it as SAME or, by a recorded glitch-b5 ruling, NOT COMPARABLE); NOT COMPARABLE (known weaker or different for that arm; any partial check still runs and must pass, and the study publishes the check as NOT COMPARABLE for that arm); COUNTED BY SWEEP (account-email only, rows below the table say why it is at least as wide as C's read).
What PENDING does, per road (review 52b1f37 finding 3): on the take road a PENDING row is a refusal under the reason id named in its row with "no vendor reader yet", and after the agent's first turn every operator reason routes harness-error (routing.json driver_decided_reasons' source text: the generic operator-reason rows), so the take is refused, harness-error.
On the walk road a PENDING row is recorded in check.json like any reason; the walk is graded, and it counts as coverage only as a Claude Code walk with that reason does (pending_walk.checker_standing, D/pending_walk.py:150-208: never counted when the reason is in CONSTANT_BOUND_REASONS, D/check_take.py:2452-2453); the freeze (plan section 7, leg ii) keeps any arm with an unsettled PENDING row out of a frozen order either way.
No PENDING refusal is written under an event id (study-materials-reached, account-email, read-outside-the-checkout: check4 lifts those into events and raises CheckRefused when a lifted id disagrees with its count, D/check_take.py:1970-1982); a PENDING item on a reach row refuses under transcript-unreadable.
